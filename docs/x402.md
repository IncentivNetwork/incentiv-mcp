# Paying for x402 resources

[x402](https://x402.org) lets a website or API charge per request: it answers HTTP `402 Payment Required` with a price, and the client retries with a signed payment. The local wallet pays these in USDC from its smart account on Incentiv (`eip155:24101`), with the `incentiv-userop` scheme of [`@incentiv/x402`](https://github.com/IncentivNetwork/incentiv-x402-public). Sellers using that package (with `@x402/express`, `@x402/next` or `@x402/hono`) can be paid; resources that only accept other networks or the `exact` scheme cannot.

x402 is off until local policy enables it. The three tools are available only in the local stdio server, because they make requests from your computer.

## Tools

| Tool | Does | Signs |
| --- | --- | --- |
| `discover_x402_resources` | Lists or searches the facilitator's catalog (Bazaar) for resources this wallet can pay, with the same compatibility checks as a live payment. Every text field of a listing, tags included, is third-party text, screened when Wormhole screening is on. | No |
| `get_x402_payment_requirements` | Needs x402 on in local policy, the site allowed, the wallet enabled and its policy unexpired; otherwise nothing is sent. Sends the request once without payment and reads the 402: price, seller address, whether this wallet can pay and whether policy allows it (the x402 rules and the USDC per-transaction cap). The request is sent as given, so an endpoint that asks no payment acts on a `POST`; the tool is not marked read-only. | No |
| `pay_x402_resource` | Pays the live price, if it is at most `max_amount` and within policy, and returns the resource's answer. | Yes |

A typical flow is to discover a resource, check its price, then pay with a fresh `request_id`:

```json
{ "url": "https://api.example.com/weather?city=Kyiv", "max_amount": "0.05", "request_id": "6f1c…" }
```

`method` is `GET` (default) or `POST` with a `body`. `headers` adds request headers such as an API's own parameters; payment and transport headers are refused. `gas_token` is `USDC` (default, through the paymaster) or `native`.

A resource that needs no payment acts on the first, unpaid request. The wallet binds every `POST` to its `request_id` before sending it. After a POST may have reached the resource, the wallet resends it under that ID only with identical arguments and a nonblank `Idempotency-Key` that the seller honours. If a later retry asks for payment, the wallet preserves the earlier outcome and sends no payment. For a POST without a key and with an unknown outcome, a retry returns `x402_request_uncertain`. Check whether the seller acted before using a new request ID. Use `GET` only for requests that are safe to repeat.

A valid x402 v2 challenge on the first unpaid POST shows the resource has not acted, even if the wallet cannot pay it. The request can then change under the same ID, for example to raise `max_amount`. The wallet also allows changes after a failure that proves nothing was sent, unless the ID already had a binding. A plain 402 leaves the outcome unknown. Other unpaid HTTP errors or redirects return `request_failed` and keep the binding. A binding for a request that only got a valid challenge is dropped after a day. The others are kept, up to 10,000 bindings in total. At that limit, new POST request IDs are refused until you clear old bindings with `incentiv-mcp wallet x402 clear-bindings [--older-than-days N]` (30 days by default) in your own terminal. Clearing a binding allows that request ID to send its POST again.

The answer is returned in `content`: text as `text`, other small content as `base64`, at most 256 KiB, with `truncated` set when it was cut. It is third-party content (`third_party_content: true`), so an agent should treat it as data, never as instructions. A settled payment is also reported in the result's `_meta["x402/payment-response"]`, the key x402 MCP clients read.

## What is checked before signing

1. The URL is `https` and its host is public. Every address the name resolves to must be public, and the check runs on the addresses the connection uses. Requests always connect directly, even when Node's environment proxy (`NODE_USE_ENV_PROXY`) is on. Redirects are not followed.
2. Before the purchase tool sends any request, it checks that the site is allowed, the wallet is enabled, and its policy is current. It checks again after recording a POST binding.
3. The 402 offers `incentiv-userop` in Incentiv USDC through the pinned EntryPoint, with a payment window of 30 to 300 seconds. The live price must not exceed `max_amount`. Payment terms too large to record are refused as `x402_invalid_response`.
4. The seller address and price are allowed by the x402 policy, and the price fits the USDC limits, exposure and balance. These checks come before anything is journaled.
5. The payment operation is built like a token transfer, on its own nonce lane: the USDC gas fee to the paymaster, then the payment. The gas fee comes from the pinned paymaster's own USDC fee schedule, so it does not move with the base fee. The operation must pass `@incentiv/x402`'s own check that it pays exactly the quoted amount to the quoted address, and this wallet's operation validator.
6. The usual wallet policy applies: USDC per-transaction, daily (including gas), exposure and gas-payment limits, the gas ceilings, contract permissions, balance, policy expiry, TransferGate approval and bundler simulation.

Policy expiry is checked again after simulation, just before signing, and again just before the payment first leaves your computer. The payment is journaled before it leaves. Once that write completes, `wallet disable`, policy expiry and the seller's deadline are checked once more at the request itself; a payment refused there is recorded as never sent. Nothing is paid when a check fails; the error says which. An RPC or bundler outage fails the call with `rpc_unavailable`, and its message says which request ID to retry with. During the checks before the payment is journaled, nothing is recorded, so retry with the same `request_id`. Once it is journaled and until it is signed, the record is closed as failed, so retry with a new `request_id`. After signing, in the checks just before it is sent, the payment stays signed and unsent, so retry with the same `request_id`.

## After the payment is sent

Only the seller's facilitator submits an x402 payment. The wallet never broadcasts it itself, and `wallet operation resolve` does not send it.

| Status | Means |
| --- | --- |
| `submitted` | The seller reported the settlement (`seller_reported_settlement: true`, `settlement.transaction`), even if its handler failed or the response ended after the settlement header arrived. Interrupted bodies remain undelivered. It is pending until `get_agent_operation` shows it confirmed on chain; check that before buying again. |
| `submission_unknown` | The seller did not answer, refused the payment (`seller_error`), or did not confirm settlement. Content the seller served anyway is returned with `settlement_confirmed: false`. |
| `confirmed` / `reverted` | The operation's receipt was found on chain. |
| `superseding` | A cancellation is pending. Either the payment or the cancellation will use the nonce lane. |
| `superseded` | The cancellation took the nonce lane. Nothing was paid to the seller; the cancellation's gas was. |
| `signed` | The payment was signed and journaled but never left this computer, for example because a check just before sending failed. Retry with the same `request_id` to send it; otherwise it expires unpaid. |
| `expired` | The payment never left this computer and its deadline passed. Nothing was paid. The wallet checks the lane of a payment recorded as unsent. If its nonce was used, the wallet looks for a receipt immediately, even before the deadline. |
| `failed` | A check refused it before signing. Nothing was paid. |
| `not_required` / `request_failed` | No payment record exists: the resource answered without asking for payment, or answered an unpaid request with an error or a redirect. Nothing was paid. |

While its deadline is open, `pay_x402_resource` with the same `request_id` resends the same signed payment; it never signs a second one. Every send is checked against current wallet policy, balance and base fee. Resends also repeat TransferGate checks and bundler simulation: after an uncertain attempt, for example when the process stopped before the request started, the seller may never have received it. A payment refused there is not sent and stays as it was; one the seller may hold stays reserved. When the failure proves nothing was sent (the name did not resolve, the connection was refused, or the connection or TLS session was never established), a first send is recorded as unsent again; a resend keeps its earlier status, since an earlier attempt may have reached the seller. An error on an established connection, such as a network that became unreachable, leaves the outcome unknown. A paid request waits up to 90 seconds for its answer, longer than the stock facilitator's 60-second settle window. To buy again, use a new `request_id`.

When a `GET` payment, or a `POST` with an `Idempotency-Key` header, is `confirmed`, or `submitted` with its nonce already used on chain, the same `request_id` offers the same signed payment to the seller once more. While a `submitted` payment's nonce is unused, the seller could still submit it, so it is not sent again until the chain shows it. Ordinary reconciliation rechecks the nonce lanes and canonical receipt blocks of recent payments and cancellations for 128 blocks after settlement before reporting status or using the balance for new spending; once the head reaches that margin, reconciliation verifies the settlement once more before marking it final. A settlement recorded without a block is rechecked for an hour. If an RPC cannot be read while a settlement from the last hour is still being rechecked, the call fails with `rpc_unavailable`: retry once it is available. Reads can still show older recorded settlements during an outage. Spending requires the recheck to succeed. An RPC that is behind can also show a settled payment's nonce as unused, so the wallet holds the payment again until the RPC catches up and reports that the RPC no longer shows the settlement. A settlement already marked final is not held again: a retry then fails with `rpc_unavailable` until the RPC catches up. If a reorg invalidates the receipt or makes the payment's nonce usable again, the wallet restores the outstanding reservations until the payment or its cancellation settles. The wallet cannot tell whether an answer it returned earlier reached you: the process can stop after recording the answer and before returning it. The payment can be charged only once, so a seller that still recognises it may serve the answer again at no further cost. A seller on the stock `@incentiv/x402` facilitator does not: its facilitator refuses a payment it already settled (`already_settled`), so recovering a lost answer needs a seller that keeps its answers. The result says `content_delivered: true` with the content, or `content_delivered: false` when the seller did not serve it. In that case, buying again with a new `request_id` pays again.

Any other `POST` is never sent again once it may have reached the seller, whether it settled or its outcome is unknown: a seller that accepts the payment again would run its handler a second time. Its retry returns `content_delivered: false`. Include an `Idempotency-Key` header only when the seller documents that it runs each key once.

While a cancellation is pending (`superseding`), wait until `get_agent_operation` shows `superseded` (cancelled, nothing paid), `reverted` (the payment landed but failed, so the seller was not paid) or `confirmed` (paid). A new `request_id` uses another nonce lane, so buying again before then can pay twice.

Settlement is confirmed from the EntryPoint's `UserOperationEvent`, agreed by every configured RPC. The bundle is located through the wallet's bundler, the transaction the seller reported, or, once the payment's nonce is used, a search of EntryPoint events forward from 128 blocks before the block the payment was signed at, since a reorg can re-mine it lower. Every configured RPC is searched, and each distinct transaction found is verified by all RPCs. If a log query fails, the search can still verify a receipt found by another RPC and keeps its place before the incomplete range. Each reconciliation searches at most 100,000 blocks and records its progress, so a payment that settled long after it was signed is still found. A cancellation keeps its own search start and progress. A source whose transaction fails verification, for example after a reorg, is skipped in favour of the next. A seller's facilitator that uses another bundler is therefore still reconciled.

A payment record keeps the resource URL with its query values replaced by `[redacted]`, since they can hold an API key, and only a digest of the full request and its headers. The seller's own payment terms are kept as sent, since a retry sends them back; a seller that echoes the full URL in them puts it in the local journal too. A failed, expired or cancelled payment never reached a seller and is archived as soon as it ends; a settled or superseded one is archived after two days. If its receipt block was recorded, it must also be marked final before archiving. An archived payment keeps only its request ID, a digest of its request, its outcome, its user operation hashes (including signed cancellations), and its transaction hash, so its answer can no longer be asked for again. `get_agent_operation` finds it by request ID or user operation hash and reports it with `archived: true`. A retry with an archived request ID pays nothing and reports how the payment ended: a `confirmed` one says its answer can no longer be asked for, and any other outcome says the seller was not paid, so a new request ID is needed. Archived payments are kept, so a request ID never pays twice. If the operation history nears its 12 MiB size limit, new payments pause (`policy_denied`) while transfers keep working. Archived payments alone fill it at about 35,000. Payments from the last two days are kept in full, with the seller's payment terms, so they take more room: typically a few KB each, and up to about 20 KB when a seller sends the largest terms it may. To free room, clear old archived payments in your own terminal with `incentiv-mcp wallet x402 clear-archive [--older-than-days N]` (90 by default). A cleared request ID is free again, so a retry under it pays again.

The chain does not enforce the deadline, so a payment the seller received but did not settle stays valid until its nonce is used. Its amount and gas therefore stay reserved against your daily budget until it settles or is cancelled. To cancel it, run this in your own terminal:

```sh
incentiv-mcp wallet operation resolve <request_id> --replace
```

Cancelling signs and sends a new operation, so it needs the wallet enabled; it works after the policy expires. `wallet disable` stops new payments, but it cannot recall a payment the seller already holds: to cancel one after disabling, enable the wallet again with `incentiv-mcp setup` first.

The replacement is a zero-value operation on the payment's own nonce lane, so either it or the payment executes, never both. While an x402 payment is unresolved, backups and capability approval wait for it, as they do for any signed operation.

Each payment uses its own nonce lane, so once the account is deployed, pending payments do not block transfers, swaps or other payments. While the account is undeployed, a pending payment would deploy it, so other operations and payments wait for it (`operation_pending`).

## Policy

`incentiv-mcp setup` offers x402 when the policy includes USDC. It asks for a maximum price per payment, the sites the agent may pay (blank allows any), and the seller addresses it may pay (blank allows any). The stored block is:

```json
"x402": {
  "origins": { "mode": "allowlist", "origins": ["https://api.example.com"] },
  "payTo": { "mode": "any" },
  "maxPerPayment": "100000"
}
```

`maxPerPayment` is in USDC atomic units (6 decimals). Payments also count against the USDC token limits, and the paymaster gas fee against `gasPayment`. The transfer recipient allowlist does not apply, because sellers choose where they are paid. Existing wallets keep x402 off until setup is rerun and the new permissions are confirmed.

## Costs

Gas is paid on top of the price: about 0.03 USDC through the paymaster (its minimum is 0.026 USDC), or CENT from the account with `gas_token` set to `native`. The facilitator charges nothing. A seller can serve content before or after settlement; one that settles first (`settles_before_handler` in the price) does not refund a handler that fails afterwards.

## Discovery

`discover_x402_resources` reads `https://x402.incentiv.io/discovery/resources` and `/discovery/search`. Set `INCENTIV_X402_FACILITATOR_URL` to an `https` origin to read another facilitator's catalog. Listings are not verified: their text comes from whoever paid for them, and the live 402 sets the price. With Wormhole screening on, every text field of a listing (URL, name, description, MIME type, last-updated date, each tag and the declared input) and seller error text, including the body and content type of an unpaid error response, are screened. An unpaid error body that is not text is never returned, only its size and SHA-256; resource content, paid or free, is returned as is and marked `third_party_content`.

## Mainnet acceptance suite

From a repository checkout, the opt-in suite uses the built stdio server, the live Incentiv facilitator and a temporary HTTPS seller over [localhost.run](https://localhost.run/docs/http-tunnels). It needs Node 22.18 or newer, an OpenSSH client on `PATH`, and an available OS credential store. Each run rebuilds `dist/` first. If that changed anything, it stops before testing, so that the tarball and its recorded commit match; run the same command again. The temporary tunnel uses a pinned host key and an account that requires no SSH credentials. The pinned key protects only the SSH channel: localhost.run terminates TLS, so its operator can see the signed payment in the `payment-signature` header and the seller's answer. It cannot redirect the payment, which pays only the quoted amount to the seller's `payTo`, but it could submit it to the facilitator itself. Fund the buyer with the test amount below and nothing more.

```sh
npm ci --ignore-scripts
npm run build
npm run e2e:x402 -- prepare
npm run e2e:x402 -- preflight
npm run e2e:x402 -- status
```

`prepare` preflights the public seller and creates separate buyer and seller profiles. It prints the buyer smart-account address and the exact funding amount. The suite stores the test administration credential in the OS credential store. `preflight` installs the built npm tarball in a temporary directory and checks the payable quote and policy refusals through MCP stdio. It requires no funds, and the seller blocks any signed request from reaching the facilitator.

Send **0.05 USDC on Incentiv Mainnet** to the buyer address for the funded run. Only the buyer needs funding.

```sh
npm run e2e:x402 -- run --approve-mainnet-spend
```

This authorizes one **0.01 USDC** purchase plus at most **0.04 USDC** of paymaster gas. The run repeats the free checks on the installed tarball, pays once, restarts MCP, and verifies the canonical receipt, gas charge, seller credit, buyer debit, reservation release, and same-ID replay. Add `--drop-response` to have the seller drop its first response after settlement and verify that the restarted MCP process recovers the payment. The runner supplies the public HTTPS URL and closes the tunnel on exit. It writes the funded UUID and tarball SHA-256 to `.x402-mainnet-e2e/attempt.json` before requesting payment and saves successful evidence in `.x402-mainnet-e2e/result.json`. Use `status` to reconcile that UUID after a timeout or interruption. The runner disables the buyer on completion, on a handled failure, and on Ctrl-C or SIGTERM. Keep the wallet and run records for reconciliation. A new test run requires a separate directory selected through `X402_E2E_DIR`.

To retry a failed preparation after fixing the build, run `npm run e2e:x402 -- run --approve-mainnet-spend --retry-failed`. The runner verifies that the wallet archived the original attempt as failed without recording a user operation or transaction, and that the buyer still holds the exact original funding. It retains the earlier attempt alongside the new one.

Only one run may use a directory at a time; it holds `.x402-mainnet-e2e/running`, which records its process and host. If a run was killed, `npm run e2e:x402 -- unlock` removes that marker once its process has exited on this host, and refuses while it may still be active. It leaves any funded attempt recorded, so run `status` before running again.
